# Five rivals validate TinySteno's channel split

All five projects keep TinySteno's core idea, microphone means "me" and system audio means "them", and four of them add layers on top that make speaker handling more robust than TinySteno's today: echo/bleed suppression, an optional acoustic split of the remote channel into Speaker 1..N, and a strict fall-back to plain channel labels when the model misbehaves. None of them summarizes more rigorously than TinySteno, whose schema-validated, chunked extraction is the strictest design of the six; where they are ahead is in the context they feed the model (label meanings, timestamps, meeting date, user notes) and in refusing to save silently empty or partial results. The most urgent findings are in TinySteno itself: with diarization off, which is the default, a stereo recording is transcribed from the microphone channel only, so **remote participants never reach the transcript or the summary**, and the API backend emits two monolithic blocks instead of the interleaved transcript the README shows. The right backend move is to keep faster-whisper and the existing WhisperX server as the ASR engines, and add `sherpa-onnx` as an optional extra that diarizes only the system-audio channel; OpenWhispr itself is not a usable backend, but it is the best field guide to running sherpa-onnx diarization on hour-long audio. Licensing is simple with one exception: four projects are MIT, openminutes is AGPL-3.0, so its ideas must be re-implemented, not copied. Nothing here was built or run by the researchers, almost every accuracy and speed figure is the project's own, and no head-to-head measurement exists, so the recommendations below are ordered by how little they depend on unverified numbers.

## TinySteno's own code hides defects that matter more than any borrowed feature

The baseline read of TinySteno at `61b8881` (v0.2.4) was code-only, but several of its findings are deterministic consequences of the source and need no benchmark to confirm. The most serious: `convert_to_16khz_array` keeps only channel 0, and both backends push the full stereo array through it for the plain transcript, so when `diarization` is false (the default in `main.py`) the right channel is never decoded ([transcriber.py:56-57, 154-155](../../tinysteno/transcriber.py); [api_transcriber.py:62, 116](../../tinysteno/api_transcriber.py); [main.py:56](../../tinysteno/main.py)). A user who records a call with loopback working and default settings gets a note built from their own half of the conversation.

The API backend has three linked problems. It uploads each channel separately and joins the results as `"[You] {left}\n\n[Others] {right}"`, so conversational order is lost; it requests `verbose_json` and then reads only `text`, `language` and `duration`, discarding the segment list that would allow interleaving; and a silent diarized recording yields the non-empty string `"[You] \n\n[Others] "`, which defeats the pipeline's no-speech check ([api_transcriber.py:73-107, 126-149](../../tinysteno/api_transcriber.py); [pipeline.py:140-144](../../tinysteno/pipeline.py)). The README claims the API backend "supports the same features as the local backend" and shows interleaved output ([README.md:339-345, 398-403](../../README.md)). The local backend, for its part, runs **three full Whisper passes** when diarizing, two of them over the identical microphone signal, and reports progress for only the first ([transcriber.py:154-160, 178-189, 196-200](../../tinysteno/transcriber.py)).

The recorder contributes quieter faults. Both channels are peak-normalised against a single global maximum, so a loud side leaves the other quiet in the 16-bit file; the two streams are started sequentially and joined from sample 0 with no offset compensation; and a 2-channel microphone with no loopback is written as a stereo WAV that the transcribers then label left = You, right = Others, a mistake the setup wizard encourages by telling users diarization "requires stereo recording (channels = 2)" ([recorder.py:375-385, 276-305, 455-456](../../tinysteno/recorder.py); [main.py:630-654](../../tinysteno/main.py)).

Summarization degrades silently at every failure point. Chunks whose fields come back empty are dropped with no trace in the note; if the merge call fails, `_extract` returns all-empty fields and **the successful partials are thrown away**; a string returned where a list was expected becomes `[]` instead of a one-item list; and there is no retry or re-prompt beyond the SDK's transport-level default ([orchestrator.py:55-70, 199-216, 234-245](../../tinysteno/orchestrator.py)). Smaller defects are cheap to close: the exporter overwrites an existing note with the same title and date; `generated_tags` and `tags` are not in `_RESERVED_NAMES` despite the project instructions saying they are; the `sprint` persona's title and tags are generated from the one-word `ceremony_type` field; the `rca` persona asks for real timestamps the transcript does not carry; `pywhispercpp` is a declared but unused dependency; and a failed later stage followed by a retry re-transcribes from scratch because the transcript is never persisted on its own ([obsidian.py:45-51, 68-72](../../tinysteno/obsidian.py); [personas/__init__.py:17](../../tinysteno/personas/__init__.py); [personas/sprint/persona.yaml:5-6](../../tinysteno/personas/sprint/persona.yaml); [personas/rca/system_prompt.md:8](../../tinysteno/personas/rca/system_prompt.md); [pyproject.toml:10](../../pyproject.toml); [pipeline.py:130-201](../../tinysteno/pipeline.py)).

Three further concerns rest on outside knowledge and need a check before they are treated as fact: that CTranslate2 has no Metal backend, so the README's "Apple Silicon (MPS)" claim describes CPU execution; that a 75-minute 44.1 kHz stereo WAV read as float64 costs roughly 3.2 GB before resampling; and that single-request uploads exceed hosted Whisper limits after about 13 minutes. Two of these gain indirect support from the comparison: openminutes splits audio for upload-limited providers at a 24 MiB limit into 600 s windows ([chunked.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/packages/providers/src/transcription/chunked.ts)), and both StenoAI and anarlog have **deprecated `llama3.2:3b`, TinySteno's default summarization model** ([StenoAI config.py](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/config.py#L341-L400); [anarlog model.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/local-llm-core/src/model.rs)).

## Everyone keeps the channel prior; the winners add bleed handling and a guarded acoustic split

TinySteno has no acoustic diarization: two hard-coded labels assigned by channel index, interleaved by Whisper segment start time in the local backend only ([transcriber.py:191-207](../../tinysteno/transcriber.py)). The comparison shows this is the right foundation and an incomplete building. The table gives the verdict per project; the prose explains what each one teaches.

| Project (licence) | Speaker mechanism | Labels | Echo/bleed | Performance evidence | Versus TinySteno |
|---|---|---|---|---|---|
| OpenOats 1.x (MIT) | Channel split + optional LS-EEND on system audio, off by default | You / Them / Speaker N | Text-similarity filter; AEC hard-disabled | Upstream corpus DER only | More capable on paper, weak in practice; 2.0 reverts to TinySteno's design |
| openminutes (AGPL-3.0) | Bot scrapes active-speaker UI; sherpa-onnx diarizer for single-mic recordings | Real names, N speakers | Not applicable (one mixed stream) | Self-measured, partly synthetic | More robust attribution on bot calls; different capture model; not faster |
| anarlog (MIT, except `enterprise/**`) | Channel split + pyannote-3.1-style Rust pipeline or cloud labels + voiceprints | Names, You, Speaker N | Neural AEC + echo gate | Eval harness exists, no results published | Most complete design; heaviest; local path Apple-only |
| StenoAI (MIT) | Channel split + per-channel Sortformer (macOS) + opt-in voiceprints | You / Others / Speaker N, 4 per channel | Browser AEC + text/RMS dedup + embedding merge | Self-reported timings | Closest relative; most portable Python post-processing |
| OpenWhispr (MIT) | Channel split + sherpa-onnx pyannote-3.0 + CAM++ with heavy post-clustering policy | You / Them / Speaker N / names | Not traced | Cluster-count observations on a private set | Best source of sherpa-onnx tuning; not a backend |

### OpenOats tried neural diarization on call audio and is removing it

OpenOats 1.x runs FluidAudio's LS-EEND on the system-audio stream only, opt-in, mapping diarizer index 0 to "Them" and later indices to "Speaker N", with one label per ASR segment live and finer speaker-run slicing in an optional batch pass ([DiarizationManager.swift](https://github.com/yazinsai/OpenOats/blob/b4353cd/OpenOats/Sources/OpenOats/Transcription/DiarizationManager.swift)). FluidAudio reports DER of 20.76% on AMI, 12.11% on CALLHOME and 19.61% on DIHARD III, each on its own test set ([LS-EEND.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/LS-EEND.md)); on real conference calls users report it labelling everything as one speaker, and the project's own root-cause analysis says a mixed conferencing stream "is fundamentally harder to diarize than a room microphone" ([#506](https://github.com/yazinsai/OpenOats/issues/506)). The maintainer's 2.0 plan drops multi-speaker splitting and live transcription and converges on **two tracks, whole-track transcription after the call, You or Them by track**, which is TinySteno's architecture ([#752](https://github.com/yazinsai/OpenOats/issues/752); [PLAN.md on v2](https://github.com/yazinsai/OpenOats/blob/v2/PLAN.md)). That is the strongest signal in the whole study that splitting the remote channel is a nice-to-have with modest real accuracy, and that TinySteno's deferred whole-file decode is a strength.

What OpenOats does contribute is the cheapest bleed fix available. It hard-disables voice-processing AEC because it "conflicts with system audio capture on macOS" ([TranscriptionEngine.swift](https://github.com/yazinsai/OpenOats/blob/b4353cd/OpenOats/Sources/OpenOats/Transcription/TranscriptionEngine.swift)) and instead drops a microphone utterance that follows a system utterance within 1.75 s when word-set Jaccard similarity is at least 0.78 or one text contains the other, for utterances of at least 4 words or 20 characters ([AcousticEchoFilter.swift](https://github.com/yazinsai/OpenOats/blob/b4353cd/OpenOats/Sources/OpenOats/Transcription/AcousticEchoFilter.swift)). The 2.0 plan keeps this idea and calls echo removal on speakers "the hardest correctness problem".

### openminutes sidesteps diarization on calls and documents its limits when it cannot

On bot-joined Meet, Teams and Whereby calls openminutes does no audio diarization: it samples the page's active-speaker indicator every 250 ms and assigns each word to a named participant with a lag-corrected Viterbi path whose switch cost falls after pauses and sentence ends ([room-tracker.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/apps/bot/src/room-tracker.ts); [speaker-words.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/packages/core/src/speaker-words.ts)). That needs a Docker stack, a visible bot and scraped DOM selectors, and does not transfer to a local recorder. Its fallback for single-microphone recordings does: `sherpa_onnx.OfflineSpeakerDiarization` with pyannote segmentation 3.0, a 3D-Speaker ERes2Net embedding and threshold clustering at 0.9 ([diarize.py](https://github.com/dennisklappe/openminutes/blob/9d64ff7/services/whisper/diarize.py#L218-L233)). The author's own numbers put that diarizer at **17.2% speaker error on five real AMI meetings**, about 90% majority-speaker accuracy on ten real 2-3 person calls versus about 96% with a simulated indicator, and roughly 0.5 s of CPU per second of audio; turns under about 2 s are "the weak spot" ([docs/speakers.md](https://github.com/dennisklappe/openminutes/blob/9d64ff7/docs/speakers.md)). It is not faster than TinySteno: same faster-whisper engine, `small`/`int8` on CPU by default, though with `vad_filter=True, word_timestamps=True` and a punctuation prompt that TinySteno omits ([app.py](https://github.com/dennisklappe/openminutes/blob/9d64ff7/services/whisper/app.py#L89-L110)). The project is three weeks old with 9 stars and thresholds its author calls untuned on real audio; treat it as a notebook of well-documented ideas.

### anarlog shows what the full stack looks like, and what it costs

anarlog (the renamed Hyprnote repository) records stereo with the same channel semantics and then applies rules before models. The direct-microphone channel of a call "is never diarized"; a 1:1 call's remote channel is skipped because there is "nothing to separate"; the remote channel is otherwise diarized with speaker bounds of participants minus one; and if several participants were expected yet the system channel stayed silent, the meeting is treated as in-person and the microphone is diarized instead ([diarize.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/listener2-core/src/batch/diarize.rs)). The on-device diarizer mirrors the pyannote.audio 3.1 pipeline in Rust on ONNX Runtime, with a 12-second minimum cluster size that will absorb brief speakers ([pipeline.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/pyannote-local/src/pipeline.rs)). Echo is attacked at the signal level: a two-stage neural AEC enabled unless the output device is headphones, plus an echo gate that zeroes microphone chunks dominated by the speaker signal using cross-correlation over lags up to 1600 samples ([stream.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/listener-core/src/actors/source/stream.rs); [local_soniqo_live.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/owhisper-client/src/local_soniqo_live.rs)). Voiceprint naming is deliberately timid: cosine at least 0.62 with a 0.08 margin, mutual-unique, and no guess on a thin margin ([matching.rs](https://github.com/fastrepl/anarlog/blob/a99e237/crates/voiceprint/src/matching.rs)).

This is the most robust design studied, by construction. Its performance is unknown: an eval harness computes DER on AMI and VoxConverse and accepts changes only with real-time factor under 0.15, but no results were found ([PROGRAM.md](https://github.com/fastrepl/anarlog/blob/a99e237/crates/pyannote-local/eval/PROGRAM.md)). An open pull request also shows the hazard of word-level merging across channels, where overlapping speech "alternates channels word by word, creating a new block for almost every word" ([PR #8189](https://github.com/fastrepl/anarlog/pull/8189)).

### StenoAI is the closest relative and the best source of portable code patterns

StenoAI records stereo with microphone left and system right, transcribes each channel separately and interleaves chronologically, exactly TinySteno's shape. On macOS it then diarizes each channel with FluidAudio's CoreML Sortformer (four speaker slots per channel) through a Swift sidecar whose contract is that any failure returns `None` so the meeting falls back to channel labels ([main.swift](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L1-L60); [transcriber.py L1062-1101](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1062-L1101)). The CoreML engine does not port to Python on Linux or Windows; the Python around it does. The dominant cluster keeps `You` or `Others`; minority clusters are folded in when one cluster holds 92% of speech unless they have 15 s of speech and 1.55 s average turns; sentences are assigned by midpoint and split at word level only when long and contested ([transcriber.py L836-998, L1286-1338](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L836-L998)).

Its bleed handling is the most directly adoptable in the study. For each system segment it finds the nearest microphone segment within ±3.0 s and, at token Jaccard 0.5 or more with both sides at least 15 characters, **drops whichever side has lower RMS over that time range**; if the two channel transcripts still overlap at Jaccard 0.6 it collapses to microphone-only ([transcriber.py L643-774, L3855-3883](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L643-L774)). It also normalises loudness per channel before ASR and gates silent channels on RMS, the direct answer to TinySteno's joint peak normalisation. On naming, StenoAI tested automatic voiceprint matching against AMI, found that people sharing a room score "artificially similar to each other regardless of true identity", and removed it in favour of human-confirmed suggestions ([transcriber.py L1408-1417](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1408-L1417)). Its self-reported diarization cost is about 23 s for a 21-minute file on the Neural Engine.

### OpenWhispr documents how raw sherpa-onnx diarization fails on long audio

OpenWhispr has grown from dictation into a meeting-notes product. It diarizes exactly one channel, the system channel if any system audio was heard and otherwise the microphone, by spawning the stock `sherpa-onnx-offline-speaker-diarization` executable with pyannote segmentation 3.0 and a 3D-Speaker CAM++ embedding, about 37 MB of ungated downloads ([diarization.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/diarization.js); [meetingDiarizationInput.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/meetingDiarizationInput.js)). Its value is the scar tissue in `diarizationPolicy.js`: an earlier configuration produced **46 "speakers" on a 73-minute voice memo**; the cluster threshold now ramps from 0.6 at 15 minutes to 0.7 at 60; clusters under 1 s, or under 10% of speech with mean segments under 3 s, are dropped as phantoms; diarization is discarded entirely when one cluster holds 93% of speech; centroids are merged at cosine 0.5; and the speaker count is never forced into the clusterer because doing so "splits short utterances from long ones instead of one voice from another" ([diarizationPolicy.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/diarizationPolicy.js)). Swapping the embedding model alone moved profile recognition from 44% to 91% ([#2449](https://github.com/OpenWhispr/openwhispr/issues/2449)). openminutes reached the same conclusion about forced counts independently, applying a requested count by splitting and folding after clustering ([services/whisper/README.md](https://github.com/dennisklappe/openminutes/blob/9d64ff7/services/whisper/README.md)). These figures are the project's own observations on a small private set, and it publishes no DER.

## TinySteno already has the strictest summarizer and the thinnest prompt

No project in the set uses schema-constrained output for notes. OpenOats makes one streamed call producing free Markdown and, past 60,000 characters, **drops the middle third of the transcript** ([NotesEngine.swift](https://github.com/yazinsai/OpenOats/blob/b4353cd/OpenOats/Sources/OpenOats/Intelligence/NotesEngine.swift)); anarlog sends the whole transcript in a single call with no chunking at all ([enhance-workflow.ts](https://github.com/fastrepl/anarlog/blob/a99e237/apps/desktop/src/store/zustand/ai-task/task-configs/enhance-workflow.ts)); openminutes and StenoAI run sequential map-reduce into fixed Markdown headings ([summarize.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/apps/worker/src/summarize.ts); [summarizer.py](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L521-L601)). TinySteno's persona schema, JSON validation and Jinja2 rendering give typed, template-ready fields that none of the others have, and its LLM-generated tags are unique in the set. The persona system should stay.

Where the others are ahead is in three areas that cost little to copy. The first is context. TinySteno's model sees only the persona prompt and the transcript text, and no prompt explains what `[You]` and `[Others]` mean ([orchestrator.py:148-168](../../tinysteno/orchestrator.py)). StenoAI prepends "NOTE: [You] is the recorder, [Others] are remote participants." ([summarizer.py L1396-1425](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L1396-L1425)). openminutes renders lines as `[hh:mm:ss] Speaker: text` and passes the meeting date with an instruction to resolve "tomorrow" and weekday names to dates ([summary-job.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/apps/worker/src/summary-job.ts#L36-L37)). OpenWhispr branches its prompt on whether the transcript has speaker labels, forbids using "You" or "Them" as an action owner in the unlabelled case, and prefixes a fidelity rule that "proposed, not yet authorized, and decided are different" ([builtinActions.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/builtinActions.js); [sourceFidelity.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/sourceFidelity.js)). OpenOats and anarlog both inject the user's own typed notes, OpenOats with explicit untrusted-data framing for calendar metadata.

The second is chunk awareness. TinySteno slices at raw character offsets and sends each slice with a prompt identical to the whole-transcript prompt. StenoAI and openminutes both tell the model "This is part N of M", split on line boundaries, and re-condense hierarchically with a bounded depth and an explicit error instead of an unguarded single merge. StenoAI also sizes chunks from an explicit per-model context window, estimating a pessimistic 2 characters per token, because Ollama's small default context silently truncates; its table gives `llama3.2:3b` 8,192 tokens ([summarizer.py L102-154, L310-353](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L102-L154)). TinySteno's fixed 12,000-character chunk with no context setting sits right at that edge.

The third is failure honesty. OpenOats and StenoAI both raise when the model returns nothing instead of saving an empty note, StenoAI retries an empty map result once, anarlog validates the first characters of the stream and retries with feedback, and OpenWhispr asks for a `NOTHING_TO_SUMMARIZE` sentinel on filler-only input. StenoAI's transcript-first storage means a summary can be re-run with another model without re-transcribing, which also fixes TinySteno's retry cost. Titles in StenoAI, openminutes and anarlog are generated from the finished summary (StenoAI bounds the input at 4,000 characters), not from the first 500 characters of whichever string field comes first.

Two transcript-hygiene ideas sit between transcription and summarization. openminutes removes Whisper's invented caption credits by pattern, drops lines of five words or fewer that recur three or more times in isolation, and flags windows whose words-per-minute fall below 25% of the recording's median ([transcript-quality.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/packages/core/src/transcript-quality.ts#L52-L141)); StenoAI drops runs of five or more identical segments. Both target exactly the failure TinySteno invites by decoding a mostly silent channel without VAD. LLM transcript clean-up passes exist (OpenOats' line-count-preserving cleaner, anarlog's id-preserving JSON Patch contract, which has no caller in the app) but none is evidence of a quality gain, and they are not a priority.

## The backend answer is "use the engines directly", with sherpa-onnx as an optional extra

OpenWhispr cannot serve as a backend. Its only programmatic transcription route is a token-protected loopback bridge whose `POST /v1/transcribe` takes a local file path and returns plain text with no segments, timestamps or speaker labels, and it needs the Electron app running ([cliBridge.js](https://github.com/OpenWhispr/openwhispr/blob/main/src/helpers/cliBridge.js)). Everything useful inside it is a stock upstream binary that TinySteno can call itself.

Of those, **`sherpa-onnx` is the one worth adopting**. It is an Apache-2.0 pip wheel for macOS, Linux and Windows with no listed dependencies and no PyTorch ([PyPI](https://pypi.org/project/sherpa-onnx/)), and its Python `OfflineSpeakerDiarization` API takes a mono float32 array and returns start/end/speaker segments with a progress callback ([example](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/offline-speaker-diarization.py)). The models are plain release downloads with no Hugging Face token. Upstream publishes real-time factors of 0.11 to 0.30 single-threaded on a 57-second file and no DER ([models page](https://k2-fsa.github.io/sherpa/onnx/speaker-diarization/models.html)). Two independent projects, openminutes and OpenWhispr, ship it for this purpose, which is the best available evidence that it works and that it needs the post-clustering policy described above. Its accuracy ceiling is probably below the full pyannote 3.1 pipeline, since it shares the segmentation model but uses a different embedding and simpler clustering; that ranking is a judgement, not a measurement. The `sherpa-onnx-reverb-diarization-v1` model is non-commercial and should be avoided, and the redistribution terms of the converted pyannote segmentation model were not examined.

The maintainer's WhisperX server is the higher-ceiling route for personal use. pyannote `speaker-diarization-3.1` publishes DER of 18.8% on AMI headset mix and 11.3% on VoxConverse and accepts `num_speakers`, `min_speakers` and `max_speakers`, but it is gated behind a Hugging Face token and pulls in PyTorch ([model card](https://huggingface.co/pyannote/speaker-diarization-3.1)). That weight is acceptable on a server and wrong for a default client install. The research did not examine the server itself, so what it returns over the OpenAI-compatible route TinySteno uses is unknown; statements about WhisperX here rest on general knowledge. What is certain from TinySteno's code is the prerequisite: `ApiTranscriber` must start reading the `segments` array it already requests, because both interleaving and any server-side speaker label arrive there.

The other candidates rank lower. whisper.cpp's server can be mounted at `/v1/audio/transcriptions` and returns `verbose_json` with segments and words, with Metal, CUDA and Vulkan builds, which makes it a plausible Apple Silicon speed-up through the existing API backend; its `diarize` flag is only a per-segment stereo energy comparison on a single mixed decode, weaker than TinySteno's two independent decodes ([server.cpp](https://github.com/ggml-org/whisper.cpp/blob/master/examples/server/server.cpp)). Parakeet TDT v3 edges Whisper large-v3 on the Open ASR Leaderboard, 6.34% average WER on NVIDIA's card against 7.44% in the leaderboard paper, but covers only 25 European languages, and the headline RTFx of 3,333 is a GPU figure ([NVIDIA model card](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3); [arXiv 2510.06961](https://arxiv.org/html/2510.06961v3)). On Apple Silicon the claimed speeds are about 81x real time for parakeet-mlx in a single contributor's issue and about 2 minutes per hour of audio on an M1 in OpenOats' plan ([StenoAI #360](https://github.com/stenolabs/stenoai/issues/360); [PLAN.md](https://github.com/yazinsai/OpenOats/blob/v2/PLAN.md)). StenoAI had to window MLX decoding at 60 s with 15 s overlap after a 33-minute meeting tried to allocate about 40 GB ([_parakeet_mlx.py](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/_parakeet_mlx.py#L48-L59)). Parakeet is a reasonable third backend later, after a local timing test.

## What is measured, what is claimed, and what is inferred

Nothing in this report was measured by the researchers. No project was built or run, TinySteno included, and no shared benchmark exists, so "more robust" and "more performant" are architectural judgements throughout.

The firmest evidence is code read at pinned commits: OpenOats `b4353cd`, openminutes `9d64ff7`, anarlog `a99e237`, StenoAI `f4bbe81`, OpenWhispr `2eb67aa`, TinySteno `61b8881`. Mechanisms, thresholds and prompts cited from source are reliable as descriptions of what the code does, and the TinySteno defects above are of this kind. All five upstream projects move fast; OpenOats is mid-rewrite, and its README privacy section already contradicts its code.

Self-reported figures form the second tier and are the only numbers available: openminutes' 17.2% AMI speaker error and 0.5 CPU-seconds per audio second, partly on synthetic TTS voices; OpenWhispr's cluster-purity and speaker-count observations on a private set; StenoAI's 23 s for 21 minutes and its bleed-similarity ranges, alongside thresholds its own comments call "judgment value, not a measured optimum"; FluidAudio's corpus DERs, read at HEAD and not at the versions pinned by OpenOats or StenoAI; and upstream model cards. anarlog publishes no accuracy or speed figures at all. Thresholds tied to a particular embedding model (0.62/0.08 in anarlog, 0.6/0.03 in OpenWhispr, 0.9 clustering in openminutes) do not transfer to a different model unchanged.

The third tier is inference: that bleed duplicates appear in TinySteno on laptop speakers, that Whisper hallucinates on its silent channel, that faster-whisper runs on CPU on Apple Silicon, that sherpa-onnx trails pyannote 3.1, and every better/worse verdict in the tables. The per-project comparison notes also took TinySteno's behaviour from a brief and did not re-read its code, so the baseline analysis is the authority where they differ.

## A prioritised adoption plan

The ordering puts deterministic bug fixes first, then changes that need no new dependency, then the optional diarization extra, then things to defer. Effort is a rough judgement.

Recommendation 7 deserves a caution: OpenOats' own users still report duplicated speech under both labels on laptop speakers after its text filter, and text matching cannot catch bleed that Whisper garbles differently on each channel ([#279](https://github.com/yazinsai/OpenOats/issues/279)). StenoAI's RMS tie-break and whole-transcript backstop are the reason to prefer its variant, and recommendation 6's VAD reduces how much bleed gets decoded in the first place. Recommendation 11 should be sold to users honestly as a best-effort split: the only real-call figure in the study is openminutes' roughly 90% majority-speaker accuracy on small calls, and OpenOats abandoned the feature. If rows 11 and 12 both land, the uncertainty they introduce should flow into the summary the way openminutes does it, by marking doubtful labels and telling the model that a guessed speaker must not own an action item ([transcript-text.ts](https://github.com/dennisklappe/openminutes/blob/9d64ff7/packages/core/src/transcript-text.ts#L6-L7)).

## Conclusion

The comparison changes the question. It began as "whose diarization should TinySteno copy" and ends closer to "TinySteno's architecture is where the field is converging, so finish it". OpenOats is rewriting toward two tracks and post-call transcription; OpenWhispr's users are asking for deferred whole-file transcription that TinySteno already does; anarlog and StenoAI treat the channel split as a hard prior and spend their engineering on the rules around a diarizer, not on the model. The durable lesson across all five is that robustness comes from guard rails, such as never diarizing the clean microphone, never forcing a speaker count, never naming a voice without confirmation, and always falling back to channel labels, and those guard rails are small, portable and mostly MIT.

The missing ingredient is measurement, and TinySteno is unusually well placed to supply it. Its stereo WAVs preserve the channel separation that OpenOats discards, so a handful of the maintainer's own recordings, hand-labelled once, would settle the questions this report can only rank by plausibility: how often bleed duplicates occur, whether `vad_filter` removes silent-channel hallucinations, how sherpa-onnx compares with the WhisperX server on real calls, and what each costs in wall time. anarlog's keep-a-change-only-if-DER-improves rule is the model to follow, and it would make TinySteno the only project in this set with published numbers of its own.
