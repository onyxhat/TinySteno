## 1. Diarization: does StenoAI diarize, and how?

### Takeaway
Yes, in three layers: (1) channel separation (mic = `[You]`, system audio = `[Others]`) on every platform, including live; (2) on macOS only, post-hoc acoustic diarization of each channel separately with FluidAudio's CoreML Sortformer (4 speaker slots per channel; optional Nemotron 3 with 8), giving `Speaker 2`, `Speaker 3`, and so on; (3) optional, off-by-default, human-confirmed cross-meeting naming using WeSpeaker 256-dimension voiceprints. It also has explicit text- and embedding-based echo/bleed handling that the TinySteno baseline lacks.

### Cited Findings

**Layer 1: channel labels (all platforms, live and batch)**
- The recording is a single stereo WebM/Opus file with "mic in channel 0 (L), system in channel 1 (R)"; the backend "splits the channels, transcribes each separately with per-segment timestamps, and emits a chronologically interleaved `[You]` / `[Others]` transcript". Verified in code comment and implementation. — [useSystemAudioCapture.ts L28-47](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/renderer/src/hooks/useSystemAudioCapture.ts#L28-L47); [transcriber.py `transcribe_diarised` L3705-3985](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L3705-L3985)
- Each channel passes an RMS energy gate (`MIN_RMS_THRESHOLD = 0.0003`, about -70 dB) before transcription; silent channels are skipped. A channel that hard-fails makes the whole result `transcription_failed` (audio preserved) rather than saving a partial transcript; an energetic channel that returns empty text only fails the meeting if no channel produced text. — [transcriber.py L120-124](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L120-L124); [L3729-3853](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L3729-L3853)
- Live transcript also carries per-channel attribution: two independent `_LiveVadPipeline` instances, one per channel, "so speaker identity comes from which channel actually contains the speech, not a post-hoc RMS guess on a pre-mixed mono stream". — [simple_recorder.py L2482-2500](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L2482-L2500)

**Layer 2: acoustic per-channel diarization (macOS only, post-hoc)**
- Implemented as a separate Swift executable, `diarize-sidecar` (binary `steno-diarize`), depending on FluidAudio pinned at 0.17.1, macOS 14+. — [Package.swift](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Package.swift); [Package.resolved](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Package.resolved)
- Header comment: "offline speaker diarization + voiceprint embeddings via FluidAudio's Sortformer or Nemotron 3 (both CoreML) + WeSpeaker". Default engine `sortformer` is a "4-speaker-slot streaming Sortformer. SortformerConfig.numSpeakers is hardcoded to 4; there is no speaker-count hint to pass". Optional `nemotron3` is "NVIDIA's 8-speaker streaming Sortformer (100M params, 10 ms output resolution)", selected by env `STENOAI_DIARIZE_ENGINE` / config key `diarization_engine` (default `"sortformer"`). — [main.swift L1-60](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L1-L60); [DiarizationEngine.swift](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/DiarizationCore/DiarizationEngine.swift); [config.py L1121, L2360-2379](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/config.py#L1121)
- It is end-to-end neural diarization (the model emits per-frame speaker-slot probabilities), not an embedding-then-cluster pipeline. Sidecar output is one JSON line: `{"segments":[{"speakerId":"SPEAKER_0","start":..,"end":..}], "speakers":{"SPEAKER_0":[256 floats]}}`. — [main.swift L33-38, L617-757](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L617-L757)
- Offline-tuned config: uses `SortformerConfig.highContextV2` (27.2 s per CoreML invocation) rather than the streaming default (0.48 s), "~56x" fewer invocations ("~22,500 vs ~400 invocations for a 3-hour recording"). Recordings shorter than the ~30.4 s minimum window are padded with silence to 90 s and segments clipped back. V2 was chosen over V2.1 because FluidAudio's docs say V2.1 "may degrade when many speakers are talking simultaneously". Runs on the Neural Engine (`.cpuAndNeuralEngine`). Segments under 0.25 s are dropped as noise blips. — [main.swift L69-72, L109-116, L636-675](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L636-L675); [ShortRecording.swift](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/DiarizationCore/ShortRecording.swift); [ModelReadiness.swift L34](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/DiarizationCore/ModelReadiness.swift#L34)
- Performance claims (project's own, not verified by me): a real ~21-minute file dropped to "~23s" for segmentation plus embedding after the highContextV2 switch; a ~3.5 h recording previously took "~18 minutes for the embedding-extraction phase alone"; changelog says "Diarization is roughly 6.65x faster". — [transcriber.py L148-159](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L148-L159); [changelog.mdx L102](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/docs/changelog.mdx#L102)
- Diarization is run on each channel WAV independently (mic and system), and on the whole file for mono imports (`_transcribe_diarised_mono`). Audio is decoded through ffmpeg, not CoreAudio. — [transcriber.py L3885-3910, L3992-4052](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L3885-L3910); [main.swift L40-46](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L40-L46)
- Fail-safe contract: `_run_steno_diarize` "Returns None on ANY failure — missing binary, timeout, non-zero exit, or unparseable output — so callers always have a safe fallback to legacy channel-only labeling and this can never fail a meeting". Models are an optional download; if not prepared the sidecar exits with code 3. — [transcriber.py L1062-1101](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1062-L1101); [main.swift L600-612](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L600-L612)

**Aligning ASR text to diarizer turns**
- Diarizer segments are merged when the same speaker resumes within 0.3 s (`STENO_DIARIZE_MERGE_GAP_S`) and overlapping segments are clamped so each instant belongs to one speaker (nested segments left alone). — [transcriber.py L133-138, L785-833](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L785-L833)
- Assignment is sentence-level by midpoint; a sentence of 5 s or more that overlaps more than one diarizer speaker is split at word level using Parakeet token timestamps; text more than 1.0 s away from any diarizer segment is "unplaceable" and kept under the plain channel label rather than attributed. "Text is never dropped." — [transcriber.py L836-998](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L836-L998)
- Label policy: the cluster with the most speaking time keeps `You`/`Others`; others become `Speaker N`. If one cluster holds 92% or more of the channel's speech, minority clusters are folded into it unless they have at least 15 s of speech and an average turn of at least 1.55 s, "This keeps many tiny echo/crosstalk fragments from adding up to a false additional speaker." — [transcriber.py L161-169, L1286-1338](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1286-L1338); [speaker_suggestions.py L95](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/speaker_suggestions.py#L95)
- Punctuation-only ASR segments are filtered so they cannot create phantom speakers. — [transcriber.py L1671-1680](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1671-L1680)

**Echo / bleed handling (no headphones)**
- Capture side: the mic stream is requested with `echoCancellation: true, noiseSuppression: false, autoGainControl: false`. — [useSystemAudioCapture.ts L268-272](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/renderer/src/hooks/useSystemAudioCapture.ts#L268-L272)
- Per-segment text dedup: for each system segment, find the nearest mic segment starting within ±3.0 s; if token Jaccard is 0.5 or more (both at least 15 characters), drop the side with lower RMS over that time range ("the channel with HIGHER RMS holds the direct signal"); ties drop the system side. — [transcriber.py L61-89, L643-774](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L643-L774)
- Whole-transcript backstop: if the remaining channels still have token Jaccard of 0.6 or more, collapse to mic-only. The comment claims "True bleed ... is consistently >0.8 in practice; a real two-party call ... is typically <0.2." — [transcriber.py L61-66, L3855-3883](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L3855-L3883)
- Cross-channel speaker reconciliation: because each channel is diarized independently, a leaked voice can appear as a speaker in both; clusters are merged only for mutual-nearest embedding pairs at cosine distance 0.10 or less with a 0.05 runner-up margin. — [transcriber.py L140-146, L1852-1900](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1852-L1900); [speaker_suggestions.py L118](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/speaker_suggestions.py#L118)
- Live equivalent: `_PendingFinalsCoordinator` holds each finalised utterance for at least 0.5 s (up to the 3 s bleed window) so a same-instant utterance on the other channel can be checked for bleed before display. — [simple_recorder.py L2289-2330](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L2289-L2330)

**Layer 3: speaker embeddings, naming, cross-meeting identity**
- Embeddings come from FluidAudio's bundled WeSpeaker model: overlap-excluded per-speaker masks (any frame with two or more active speakers is zeroed for all), 10 s windows, L2-normalised mean centroid per speaker, 256 dimensions. Failure returns an empty map and never fails diarization. — [main.swift L48-60, L316-548](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L316-L548); [speaker_schema.py L11](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/speaker_schema.py#L11)
- Only the user's own voice is matched automatically: an enrolled self voiceprint (cosine distance below 0.40) re-anchors `[You]` onto the matching mic cluster, so a guest who talks more is not labelled "You". — [transcriber.py L1360-1466](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1360-L1466)
- Automatic naming of other people was removed deliberately: "validating it against real ground truth (the AMI Meeting Corpus, individual headset mics) found that people sharing a room/mic score artificially similar to each other regardless of true identity ... Silent, fully automatic named matching isn't safe; named identification is now a human-confirmed suggestion". — [transcriber.py L1408-1417](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L1408-L1417)
- Suggestion thresholds: distance 0.40, margin 0.10, minimum 20 s of speech, at least 3 segments, average turn at least 1.55 s, at least 2 confirmed meetings. Per-meeting data goes to a `{stem}_speakers.json` sidecar plus a per-turn manifest of exact cluster ids used for relabelling. — [speaker_suggestions.py L65-118, L655-720](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/speaker_suggestions.py#L65-L118); [transcriber.py L3925-3974](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L3925-L3974)
- Docs: speaker identification is "optional and off by default"; a review panel lets the user approve, rename, mark a group as multiple people, and play excerpts; "it never assigns the name without review". — [speaker-labels.mdx](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/docs/features/speaker-labels.mdx)
- Participants in the note come from confirmed speaker names and (opt-in, macOS) phone/FaceTime caller ID, not from the LLM. — [speaker_suggestions.py `confirmed_participant_names` L1796](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/speaker_suggestions.py#L1796); [simple_recorder.py L8298-8358](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L8298-L8358)

### Inferences
- (Inference) Overlapped speech within a channel is not transcribed per speaker: Sortformer can emit overlapping segments, but StenoAI clamps them to one speaker per instant and assigns each ASR sentence or word to one segment. Evidence: `_clamp_overlapping_diar_segments` and `_assign_asr_segments_to_diar_segments`. Overlap across channels (you and a remote speaker talking at once) is handled naturally, as in TinySteno.
- (Inference) Speaker labels are stable only within one meeting unless the user opts into identification; `Speaker N` numbering is per-run. Evidence: sidecar comment that ids are "opaque per-run cluster labels" ([main.swift L631-634](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/main.swift#L631-L634)).
- (Inference) The whole acoustic layer is unavailable to a Python/Linux/Windows tool as-is, because it depends on CoreML and the Neural Engine through a Swift package. The portable parts are the Python post-processing (bleed dedup, dominance folding, sentence/word alignment, fail-safe fallback).

- I did not fetch FluidAudio's own documentation or model cards, so descriptions of Sortformer/Nemotron 3/WeSpeaker behaviour rest on StenoAI's code comments and the API calls it makes, not on upstream docs. Issue #359 names the model as `diar_streaming_sortformer_4spk-v2.1` while the code selects the `highContextV2` (V2) preset; I did not resolve which upstream checkpoint ships.
- No diarization error rate (DER) for StenoAI's own pipeline was found; the only DER figures are quoted from the Nemotron 3 model card in a comment ([DiarizationEngine.swift L18-26](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/diarize-sidecar/Sources/DiarizationCore/DiarizationEngine.swift#L18-L26)).

## 2. Capture model

### Takeaway
Capture happens in the Electron renderer with Web Audio, not in Python: mic via `getUserMedia`, system audio via a CoreAudio Process Tap on macOS 14.4+ (not ScreenCaptureKit), WASAPI loopback on Windows, and PipeWire `pw-record` on Linux, merged into one stereo WebM/Opus file (L = mic, R = system) written to disk every second.

### Cited Findings
- Single recording path for all platforms; stereo layout L = mic, R = system; mic-only when loopback is off (R silent). — [useSystemAudioCapture.ts L28-47](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/renderer/src/hooks/useSystemAudioCapture.ts#L28-L47)
- macOS uses `electron-audio-loopback` (^1.0.6) with `forceCoreAudioTap`, "CoreAudio Process Taps ... rather than ScreenCaptureKit"; README: "Screen Recording access is not required". — [main.js L266-296](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/main.js#L266-L296); [package.json L104](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/package.json#L104); [README.md L60, L326](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/README.md#L60)
- Each source is forced to mono and routed through a `ChannelMergerNode(2)`; `MediaRecorder` at `audio/webm;codecs=opus`, 128 kbps, `recorder.start(1_000)` "so a crash mid-recording loses at most ~1s of audio". — [useSystemAudioCapture.ts L434-473, L599-641](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/renderer/src/hooks/useSystemAudioCapture.ts#L599-L641)
- No per-app capture: "System audio capture records all audio playing on your Mac". No recording length limit. — [recording.mdx](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/docs/features/recording.mdx)
- A parallel tap feeds interleaved stereo PCM to the Python `transcribe-stream` sidecar for live text (Parakeet engine only). — [useSystemAudioCapture.ts L49-62, L507](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/app/renderer/src/hooks/useSystemAudioCapture.ts#L49-L62); [simple_recorder.py L2514-2518](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L2514-L2518)

### Inferences
- (Inference) The on-disk layout is the same idea as TinySteno's (stereo, mic left, system right) but lossy Opus rather than WAV, with browser AEC applied to the mic. Evidence: the capture code above.

### Gaps
- I did not read the full capture hook (57 KB) for sample rate, pause/resume, or device-change handling.

## 3. Transcription engine and performance

### Takeaway
Default ASR is NVIDIA Parakeet TDT 0.6B v3 (MLX on Apple Silicon GPU; ONNX Runtime CPU elsewhere), with whisper.cpp `large-v3-turbo` as the alternative for non-European languages and an optional OpenAI-compatible cloud endpoint. Parakeet gives live VAD-gated transcription plus a separate batch pass after stop; batch uses fixed 60 s windows with 15 s overlap and keeps word-level timestamps.

### Cited Findings
- Engines and defaults: `transcription_engine` default `"parakeet"`, `whisper_model` `"large-v3-turbo"` (the only curated Whisper tier, 1.6 GB), plus an ivrit.ai Hebrew fine-tune used when Hebrew is pinned or detected at probability 0.5 or more. — [config.py L1116-1117](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/config.py#L1116-L1117); [whisper_models.py L31-66](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/whisper_models.py#L31-L66)
- Parakeet backends: `mlx-community/parakeet-tdt-0.6b-v3` via `parakeet-mlx` on darwin; `istupakov/parakeet-tdt-0.6b-v3-onnx` (int8, about 670 MB) via `onnx-asr` on Windows/Linux; whisper via `pywhispercpp`. No PyTorch. — [parakeet.py L1-18](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/parakeet.py#L1-L18); [requirements.txt](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/requirements.txt)
- Batch chunking: `PARAKEET_CHUNK_DURATION_S = 60.0`, `PARAKEET_CHUNK_OVERLAP_S = 15.0`. Reason given: without chunking "a 33-min meeting tries to allocate ~40 GB on MLX and SIGABRTs". The library merges windows with global timestamps. — [_parakeet_mlx.py L48-59, L255-262](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/_parakeet_mlx.py#L48-L59)
- Word-level timestamps: each sentence segment carries `tokens` with start/end, used by the diarization aligner. — [_parakeet_mlx.py L306-342](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/_parakeet_mlx.py#L306-L342)
- Pre-processing: ffmpeg high-pass at 90 Hz plus single-pass loudnorm `I=-16:TP=-1.5:LRA=11`, applied per channel (a later fix "recover quiet microphone speech in stereo recordings", PR #521). — [transcriber.py L91-98, L3748-3761](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/transcriber.py#L91-L98)
- Live path: Silero VAD (ONNX, 32 ms frames, thresholds 0.50/0.35, 600 ms redemption) closes utterances; each is batch-decoded; partials re-decode the trailing 15 s every 0.4 s; utterances capped at 30 s. ## 4. Transcript processing and summarization

### Takeaway
The default path asks the LLM for free Markdown with four fixed English `##` headers and parses it by header, streaming tokens to the UI; JSON is a legacy path. Long transcripts (local/remote Ollama only) go through a sequential map step, an optional hierarchical re-map (max depth 2), then one streaming reduce, with chunk size derived from an explicit per-model `num_ctx`. There is no transcript clean-up LLM pass; the only pre-processing is stripping `[MM:SS]` timestamps.

### Cited Findings

**Pipeline shape**
- Transcript-first: the transcript is always saved; summarization is a separate stage gated by `auto_summarize_enabled`, and can be re-run later from the stored transcript without re-transcribing. — [MECHANICS.md, "Core Data Flow"](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/MECHANICS.md); [simple_recorder.py L1444-1571](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L1444-L1571)
- Summarizer input is the diarised text (`text_for_summary = diarised_text or transcript_text`) with leading timestamps stripped by `_strip_leading_timestamps`. — [simple_recorder.py L1444](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/simple_recorder.py#L1444); [summarizer.py L26-37, L1591](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L26-L37)
- Routing in `summarize_transcript_streaming`: template report (single call, no chunking) / map-reduce if `_needs_chunking` / single streaming call otherwise; an all-whitespace stream raises instead of saving an empty summary. — [summarizer.py L1574-1619](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L1574-L1619)

**Context window and chunking**
- Ollama's default context is small and silently truncates, so every call sets `num_ctx` per model (table: gemma4 variants, qwen3.5:9b, gpt-oss:20b = 32768; llama3.2:3b = 8192; unknown = 32768; clamp 8192 to 131072), kept identical across calls because "Ollama reloads the model when num_ctx changes". — [summarizer.py L102-154, L300-308](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L102-L154)
- Chunk when `(len(transcript)+len(notes)) / 2 > num_ctx * 0.8`, using a pessimistic 2 characters per token ("worst-case German/BPE"). Only for `local`/`remote` providers; cloud and adapter never chunk. — [summarizer.py L130-137, L506-519](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L506-L519)
- Chunk budget = `(num_ctx - 300 - 600) * 2` characters; split on the last newline within the final 20% of the chunk, else hard cut; 5% of the previous chunk is prepended as overlap. — [summarizer.py L310-353](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L310-L353)
- Map calls are sequential (the docstring says "parallel map" but the code is a plain `for` loop), non-streaming, capped at `num_predict = 600`, with one retry on an empty result. If combined map output exceeds 70% of `num_ctx` (at 4 chars/token), the map outputs are re-chunked and re-mapped, max depth 2, else `ValueError("Meeting is too long to summarize even after chunking ...")`. — [summarizer.py L416-450, L521-601](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L521-L601)
- All Ollama calls pass `think=False` so reasoning tokens do not consume the output budget, with a retry without the parameter for older remote servers. — [summarizer.py L367-437](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L367-L437)

**Prompts (verbatim, important parts)**

Be concise.\n\nKEY POINTS\n- ...\n\nDECISIONS\n- ...\n\nACTION ITEMS\n- [owner] action (deadline if mentioned)\n\nOPEN QUESTIONS\n- ...\n\nTRANSCRIPT SEGMENT:\n{chunk}" — [summarizer.py L355-365](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L355-L365)

Start directly with ## Summary." followed by the same four-section skeleton and "Only include information explicitly discussed. Do not infer or assume. If there are no action items, leave that section empty with no bullets." — [summarizer.py L452-504](https://github.com/stenolabs/stenoai/blob/f4bbe8176d409eaab65c71f23773a466035d84e5/src/summarizer.py#L452-L504)

## 5. Better, worse, or absent relative to the TinySteno baseline

### Takeaway
StenoAI is clearly ahead on speaker separation (more than two speakers, echo handling, live labels) and on local-LLM operational robustness; TinySteno's schema-driven per-persona JSON extraction is stricter than anything StenoAI does. Every item below is my inference from the cited code, not a measured result.

### Cited Findings
The evidence for each judgement is the code already cited in sections 1 to 4; the baseline description is the one supplied in the task brief (I did not read TinySteno's code for this note).

### Inferences

**StenoAI does better (inference; evidence in brackets)**
- More than two speakers: per-channel Sortformer split yields up to 4 voices per channel (8 with Nemotron 3) vs TinySteno's fixed two labels. [main.swift L11-22; speaker-labels.mdx] macOS only.
- Echo/bleed without headphones: browser AEC, per-segment Jaccard + RMS dedup, whole-transcript collapse, embedding-based cross-channel merge. TinySteno as described has none, so a speaker-phone meeting would duplicate remote speech under `[You]`. [transcriber.py L61-89, L643-774, L3855-3883]
- Chronological interleaving at sentence level with timestamps and merged same-speaker turns. [transcriber.py L3885-3954]
- Live transcript with speaker labels. [simple_recorder.py L2482-2560]
- Graceful degradation: every diarization failure falls back to channel labels; channel failure is distinguished from silence; empty LLM output raises instead of saving an empty note. [transcriber.py L1094-1101; summarizer.py L597-601, L1608-1619]
- Local LLM handling: explicit `num_ctx`, pessimistic token estimate, `think=False`, hierarchical reduce, streaming output. [summarizer.py L102-154, L367-450, L521-544]
- User's in-meeting notes and call context are injected into the prompt. [summarizer.py L1420-1425]
- Transcript-first storage allows re-summarizing with another model or template without re-transcribing. [simple_recorder.py reprocess path; MECHANICS.md step 7]
- Audio pre-processing (high-pass + per-channel loudnorm) before ASR. [transcriber.py L91-98]

**StenoAI does worse or not at all (inference; evidence in brackets)**
- No schema-validated structured output; no per-field typed extraction per template. TinySteno's per-persona JSON schema is stricter. [summarizer.py: no `format=`; simple_recorder.py L509-557]
- No LLM tag generation was found in the summarizer (TinySteno generates tags). [function list of summarizer.py: `generate_title` only]
- Map-reduce only for local/remote Ollama; cloud and template paths are single-shot. [summarizer.py L515-516, L1592-1598]
- Map step is sequential, so long meetings on CPU are slow (comment: "the calls can be minutes each"). [summarizer.py L531-534]
- Lossy Opus recording (128 kbps) vs TinySteno's WAV. [useSystemAudioCapture.ts L602-604]
- Heavy footprint: Electron + PyInstaller Python + bundled Ollama + Swift sidecar; acoustic diarization needs macOS 14+ and Apple Silicon. Not a CLI. [README.md L198-249]
- Obsidian export is a one-way mirror with fixed layout rather than a user Jinja2 template. [obsidian-sync.js L1-23]

**Techniques worth adopting in a Python CLI (inference)**
1. Per-segment bleed dedup: ±3 s window, token Jaccard 0.5 or more, 15-character minimum, drop the lower-RMS side; plus whole-transcript Jaccard 0.6 collapse. Pure Python, no model.
2. Sentence-level chronological interleave of the two channels with `[MM:SS]` stamps, stripped again before the LLM sees the text.
3. Tell the LLM what the labels mean ("[You] is the recorder, [Others] are remote participants").
4. Per-channel loudness normalisation and an RMS gate before ASR; treat "energetic channel returned empty" differently from silence.
5. For local models: set context size explicitly, estimate tokens pessimistically (2 chars/token), cap map output, retry once on empty, add a hierarchical reduce, disable thinking.
6. A compact plain-text map prompt (KEY POINTS / DECISIONS / ACTION ITEMS with `[owner]` / OPEN QUESTIONS) with schema enforcement only at the reduce step.
7. Bound the title prompt input (4,000 characters of summary) and post-clean the output.
8. If multi-speaker separation is wanted cross-platform, the design pattern transfers even though the CoreML model does not: diarize each channel separately, keep the dominant cluster as `You`/`Others`, fold minority clusters under a dominance threshold (92% / 15 s / 1.55 s average turn), split long sentences at word level, and always fall back to channel labels. A portable engine (for example sherpa-onnx or pyannote) would have to be substituted and evaluated separately; StenoAI does not use either.
9. Do not auto-assign names from voiceprints; StenoAI tested this against AMI and removed it in favour of human-confirmed suggestions.

### Gaps
- No head-to-head measurement of either tool was run; "more robust" and "more performant" here are judgements from reading code and the project's own numbers.
